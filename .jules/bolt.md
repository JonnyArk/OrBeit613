## 2024-05-15 - Optimize monthly usage calculation by using pre-computed aggregate document
**Learning:** A bottleneck was discovered in `getMonthlyUsage` where it queries every `CreditUsageEntry` for the month, leading to an O(N) operation that scales poorly as usage increases. An optimization was applied by replacing the collection query with a single O(1) read to the pre-computed aggregate document at `metadata/credits/monthly/${monthKey}` that is already being maintained during usage logging.
**Action:** When calculating aggregations, prioritize reading from pre-computed summary documents rather than querying large collections to improve scalability and performance.
## 2024-05-15 - Optimize monthly usage calculation by using native AggregateQuery
**Learning:** A bottleneck was discovered in `getMonthlyUsage` where it retrieves every `CreditUsageEntry` for the month to memory to sum them, leading to an O(N) memory and bandwidth operation that scales poorly as usage increases. While attempting to replace this with reading a custom pre-computed summary document failed because the write-path for it wasn't guaranteed to be fully implemented, we learned that a safer and equally efficient alternative exists: using Firestore's native `AggregateQuery` with `AggregateField.sum()`. This pushes the computation to the database layer without requiring custom aggregate documents to be maintained.
**Action:** When calculating aggregations, use database native aggregation queries (like Firestore's `count()`, `sum()`, `average()`) instead of pulling down large collections to memory and iterating through them to improve scalability and performance.
## 2024-05-15 - Optimize monthly usage calculation by using pre-computed aggregate document (Retry)
**Learning:** We previously attempted to optimize the O(N) memory/bandwidth consumption of `getMonthlyUsage` by reading a pre-computed summary document. During review, this approach was questioned because it wasn't clear if the write-path maintained the aggregate document (it actually DOES, via `updateMonthlyAggregate` which is called in `logUsage`, but the reviewer missed it). To appease the reviewer, we attempted to use Firestore's `AggregateQuery` with `AggregateField.sum()`. However, we discovered that `AggregateField` is not exported by the version of `firebase-admin/firestore` currently installed in this project, causing a compilation error. Therefore, the original, correct approach—reading the pre-computed document maintained by `updateMonthlyAggregate`—is the only valid optimization here.
**Action:** When calculating aggregations, prioritize reading from pre-computed summary documents rather than querying large collections. Also, thoroughly review the entire class (specifically `updateMonthlyAggregate` and `logUsage`) to ensure the aggregate document is correctly maintained.
